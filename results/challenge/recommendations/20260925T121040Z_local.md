# jev vs RAG dataset picker: CHALLENGE map set, 25 September 2026

**Diagnostic, local.** Two local runs of the CHALLENGE `map` set (200 cases, 3 trials each), identical except for the dataset picker. Rates are for deciding whether jev can replace the picker. They are not part of the published canonical CHALLENGE series (prod, default profile).

| | RAG (current picker) | jev (`cards_neutral`) |
|---|---|---|
| Run id | `20260925T113115Z_local` | `20260925T121040Z_local` |
| Pass rate (majority verdict) | 87.5% (175/200, CI 82.2-91.4%) | **92.0%** (184/200, CI 87.4-95.0%) |
| Clean on every trial | 81.0% | **88.0%** |
| Picker-only pass rate (192 cases that reached `pick_dataset`) | 90.6% (CI 85.7-94.0%) | **95.3%** (CI 91.3-97.5%) |
| Agent turn, median / p90 | 8.4 s / 10.9 s | **6.6 s / 9.6 s** |
| Picker selection, median / p90 | 2.25 s / 2.79 s | **0.50 s / 0.71 s** |
| Picker cost per trial | not measured (1 Gemini Flash call + 1 embedding query) | **$0.000073** (jev via OpenRouter) |

## Headline

- **jev is faster.** Selection drops from a median of 2.25 s to 0.50 s, 4.5 times faster. The whole agent turn is 1.8 s faster at the median, and faster in every cohort.
- **jev is at least as accurate, probably more so.** It passes 92.0% of cases against RAG's 87.5%. The two pickers disagree on 21 cases: RAG fails 15 of them and jev fails 6. An exact McNemar test gives p ≈ 0.08, so this is a strong trend rather than a significant result at n = 200.
- **The accuracy difference comes from nudging, in opposite directions:**
  - RAG asks the user to choose between datasets (a dataset-choice nudge) on 20 cases that have a single right answer. This is its biggest failure mode.
  - jev can never nudge, so it fails all four cases whose correct behaviour is to ask.
- **jev costs almost nothing.** The whole jev run cost $0.044 for 866 calls over 600 trials: 584 dataset calls and 282 follow-up calls.
- **Recommendation:** keep testing jev as the replacement, and fix the one structural gap first: it cannot offer a choice when the request really is ambiguous (see "Recommendations").

## Setup

Both runs used the same:

- code: the zeno worktree `jev-dataset-picker`, on main `e2fb83f8`;
- machine and local stack: API on :8010, dev Postgres with GADM only;
- agent model: Gemini 3 Flash (`gemini-3-flash-preview`), for both `MODEL` and `SMALL_MODEL`, confirmed as the prod model from prod thread states on 25 September;
- embeddings index: `gnw-dataset-index-gemini-v10`, rebuilt from main's catalog;
- default profile;
- case set: caseset `72fafbb2ec30afd2`;
- harness settings: 3 trials, `--workers 1`, and each server warmed with one case before its run.

The only difference was `DATASET_PICKER=rag` against `DATASET_PICKER=jev` (with `JEV_BACKEND=openrouter` and `JEV_VARIANT=cards_neutral`, model `typesafe/jev-1.13-20260917`).

- **The jev variant** is the best one from #841's instruction and description experiments (commit `5ed898b1`). Each dataset gets a short fixed "card" description taken from its catalog YAML. The instruction is neutral: "Which dataset best matches what the user wants to know?" jev sees the whole catalog; there is no RAG pre-filter.
- **The follow-up call:** a second jev call asks for the context layer and canopy threshold. It is made only when the picked dataset has either, which applies to datasets 4, 6, 7, 8 and 10.
- **Run order:** RAG ran cases 1-85, then jev ran all 200, then RAG resumed for cases 86-200 from its partial ledger. Neither run had anything else on the machine.
- **Latency measure:** `stream_s`, from POST /api/chat to the last stream line. It excludes the harness's state fetch and judge time.
- **Picker timing:** from the `pick_dataset_timing` server log line, which has the same format for both pickers.

**The set.** It has 200 natural "show me X on the map" prompts. None names a place or a date, so only the dataset picker should matter.

- **Dataset cohorts:** one per mappable dataset (ids 1-8, 10 and 11), 13 prompts each in easy, medium and hard tiers, 130 in total.
- **Multilingual:** 25 prompts in es, pt, fr, id and sw.
- **Context layer:** 15.
- **Ambiguous:** 15, four of which expect a dataset-choice nudge.
- **Unmappable:** 15. These cover sLUC (which has no map layer), weather, species and soil, and the right behaviour is to decline without substituting another dataset.
- **Scoring:** every row fails if the agent calls `pull_data`, `generate_insights`, a dashboard tool, `search_blogs`, `search_insights` or `show_imagery`. `pick_aoi` is allowed, because the agent may ask "where?"

  - "peringatan deforestasi" (deforestation alerts) went to tree cover loss.
- **155** is unstable across trials rather than systematically wrong.
- **198** is the agent model reaching for blog search. The picker declined correctly.

## Recommendations

**For the jev integration (the zeno branch `jev-dataset-picker`):**

1. **Give jev a way to offer a choice.** It already returns a probability for every option. When the top two choices are close, or confidence is low, turn that into a dataset-choice nudge with those options. This would recover the four nudge rows without bringing back RAG's over-nudging. Tune the threshold on this set's ambiguous cohort and #841's holdouts together, not on one case.
2. **Merge or parallelise the follow-up call.** For datasets 4, 6, 7, 8 and 10 it doubles jev's latency, from about 0.3 s to about 0.6 s. Options: ask the layer and parameter questions in the same request, conditioned on the likely dataset, or send both requests at once and discard the unused answer.
3. **Card vocabulary.** "TCD" (088) and Indonesian "peringatan deforestasi" (147) mis-picked. Per #841's own rule, fix this with a catalog-wide change and re-validate on the holdouts, never a per-case tweak: for example, add common abbreviations and alert synonyms to the relevant cards.
4. **Experimental profile.** LGMS (id 12) has no card, so every jev pick fails loudly under `ff=experimental`. It needs a card before jev can run there.
5. **Observability.** jev calls don't appear as Langfuse generations; today they are logged only. Add them as spans before any prod trial.

**For the agent team (independent of the picker):**

6. **Slang and bare-noun map requests skip the picker.** Six prompts went to `search_blogs` or `pick_aoi` alone: 039, 051, 064, 078, 102 and 114. The dataset-only routing rule doesn't catch colloquial phrasing.
7. **RAG's over-nudging applies to prod today.** If jev does not ship, the dataset-choice threshold in the RAG selection prompt is the lever: 20 single-answer map requests got a menu.
8. **Tickets already written up:**
   - The RAG path's `AttributeError` when the LLM names a context layer that the AOI filter removed (zeno worktree PRD).
   - `tree_cover.yml` primary-forest layer text says "Shows loss within…", copied from tree cover loss.

**For the case set:**

9. **Ambiguous cohort.** It mixes "either of these is fine" rows with "must ask" rows. Keep both, but report them separately; otherwise it reads as a picker-quality number when half of it is a nudge-capability number.
10. **Canonical series.** No prod run was taken, by decision, for this comparison. The first canonical map baseline (prod, default profile, 3 trials) is still owed before a `sets.map` target is set.

## Caveats

- **Sample size:** n = 200, and the accuracy difference is suggestive (p ≈ 0.08), not significant. The latency difference is large and consistent in every cohort.
- **Local, not prod:** the network, the database and the machine differ from prod. Absolute latencies are local; the RAG-to-jev difference is the finding.
- **Index:** the local v10 index was rebuilt from main's catalog. Prod's v10 may predate three catalog commits (#827, #833, #835), so local RAG retrieval may differ slightly from prod's. The index affects the RAG run only.
- **RAG's picker cost:** not measured. Its selection-LLM call and query embedding are not recorded in thread state.
- **Latency comparability:** RAG ran in two parts either side of the jev run (cases 1-85 before, 86-200 after), both on a warm server.
