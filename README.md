# gnw-gold-evals

This repo measures how well the agent behind Global Nature Watch (GNW) answers questions. The agent is Project Zeno, an LLM agent that answers questions about land and nature data, such as deforestation, land cover and carbon, for named places. In the GNW app it is called Horizon.

The repo holds the cases, the harness that sends them to the agent and scores the answers, and the committed results. It does three jobs:

- **CHALLENGE** measures quality and accuracy as pass rates. Its cases are phrased the way users ask, and many of them are expected to fail today: a failure is data, not a defect.
- **BENCHMARK** is a frozen, versioned subset of CHALLENGE: a fixed exam that shows whether the agent gets better. Its runs give the North Star rate that the GNW AI accuracy scorecards page shows.
- **The plain baseline** asks a plain LLM with web search the same BENCHMARK questions and scores its replies, so the agent can be compared with a general assistant.

> **GOLD moved to project-zeno on 2026-10-27.** GOLD, the capability regression suite this repo was first built for, now lives in [wri/project-zeno](https://github.com/wri/project-zeno) under `evals/gold/` (project-zeno PR #874). The GOLD files here (`cases/v1`, `cases/v2`, `results/gold/`, the GOLD skills and the manual CI release gate) are a legacy copy. The last GOLD run here is dated 31 August 2026. A later PR deletes the copy, after its case notes are reconciled with project-zeno. Do new GOLD work in project-zeno. [GOLD (legacy copy)](#gold-legacy-copy) says what is still here.

Every case is a versioned file, and every result is pinned to the exact case content it was scored against. This replaced a Google Sheet, where edits landed mid-run and nothing recorded which version of a case a score belonged to. Project terms are defined in the [Glossary](#glossary).

## How it works

A **case** is a YAML file holding a user query (or a scripted conversation) and the values a correct answer must contain: the place ids, the dataset, the date range, a figure. `evals run` sends each selected case to the agent's API, waits for the answer, then fetches the agent's final state for that conversation. **Evaluators** compare that state with the case's expected values and produce **checks**, each scoring pass, fail or not evaluated. Each check speaks for one or two of five **buckets** (retrieval, analysis, explanation, output, scope), so a failure points at the stage that broke. The run is written to `results/<suite>/runs/` as one immutable JSON record, which is committed.

What a run's numbers mean depends on the suite:

- **CHALLENGE**: `tools/challenge_rollup.py` turns a run into pass rates per set and cohort, with confidence intervals, and compares them with the targets in `cases/challenge/TARGETS.yml`.
- **BENCHMARK**: the same rollup with `--benchmark` gives the North Star rate over the version's members. `tools/benchmark_page.py` then writes the page data that the frontend shows.
- **GOLD (legacy copy)**: `tools/diff_runs.py` compares the candidate build's run with a baseline run and counts **regressions**: checks that passed before and fail now.

Results are keyed by case content, not by case name. Every case has a [uid](#uid), a hash of its query and expected values, so editing a case gives it a new uid and an old score is never read as a score for the new content. Each store of cases has a [caseset_version](#caseset-version), a hash of all its uids. There are three stores: `cases/challenge` holds CHALLENGE and every BENCHMARK member, and `cases/v2` and `cases/v1` are the GOLD legacy copy. [cases/README.md](cases/README.md) describes them and the case file.

## Setup

You need Python 3.11 or later and [uv](https://docs.astral.sh/uv/).

```bash
uv sync                                        # install, including the dev tools
uv run python -m pytest -q                     # the full suite; needs no network or secrets
uv run ruff check src tools tests generation   # lint, as CI runs it
```

The harness command is `evals` (`uv run evals run ...`). `gold` is the older name for the same command and still works, so older notes and the GOLD skills use it. The Python package is still called `goldset`: the name is historic, and over 300 import lines in more than 100 files use it, so a rename would touch most of the code for no gain.

Live runs need two secrets, set in your shell or in a `.env` file at the repo root (gitignored; `evals run` loads it before checking for a token):

- **An API token for the target environment**: `STAGING_API_TOKEN` for `--env staging`, `PROD_API_TOKEN` for `--env prod`. If that variable is not set, the CLI falls back to `API_TOKEN`, which is also the only one `--env local` reads. So a stale environment-specific token in `.env` wins over a fresh `API_TOKEN`.
- **Judge credentials**: `ANTHROPIC_API_KEY` for the default judge. With `--judge-backend openrouter-jev-decisions` the judge is TypeSafe JEV through OpenRouter Decisions, which needs `OPENROUTER_API_KEY` instead.

Cases with `expected.ground_truth` also call the production analytics API. They use `ANALYTICS_API_TOKEN` when it is set, and the API token otherwise.

## Running a suite

`evals run` sends the selected cases to the agent, scores them, and writes one run record to `results/<suite>/runs/<run_id>.json`, plus raw agent state under `results/<suite>/artifacts/<run_id>/` (gitignored). `--suite` picks the case store and the results directory together:

| `--suite` | Cases from | Results to |
|---|---|---|
| `challenge` | `cases/challenge` | `results/challenge` |
| `benchmark` | `cases/challenge` | `results/benchmark` |
| `gold` | `cases/v2` | `results/gold` (legacy copy) |

`--benchmark MANIFEST` implies `--suite benchmark` and runs exactly that version's members. There is no default suite: a run with none of `--suite`, `--benchmark` or `--cases-dir` stops with an error, so a run never lands in the wrong ledger by accident. An explicit `--cases-dir` or `--results-dir` still works and overrides the suite.

```bash
uv run evals run --suite challenge --dry-run                                   # list the selected cases; no API calls
uv run evals run --suite challenge --set aoi --env staging --build "<label>"   # smoke run of one set: 1 trial
uv run evals run --suite challenge --id ch-aoi-001 --env staging --verbose     # one case (repeat --id for more)
uv run evals run --help                                                        # every flag
```

By default every case whose status is not `not doing` runs (`--status-exclude` defaults to `not doing`). CHALLENGE's canonical runs also leave out `todo` cases: pass `--status-exclude "not doing,todo"`.

**Choose the tier before you start.**

- A **smoke run** (1 trial, the default) answers a quick question in minutes, such as "did my prompt rewrite stop the nudge?". It is never committed, never diffed and never used as a baseline.
- A run you will publish, trend or diff uses `--trials 3`. For CHALLENGE and BENCHMARK that is the **canonical run**: prod, default profile, 3 trials. For GOLD it is the **official run**: anything that produces a regression count or becomes a baseline. Three trials are needed because the agent is not deterministic: two single trials of the same build differ by more spurious regressions than a real build change produced ([Comparing two runs](results/README.md#comparing-two-runs) has the evidence). Give the run a meaningful `--build` label, such as the agent build string or a purpose like `post-fix-validation`, not the default `unknown`.

**Use the default tool profile.** Leave out `--ff` unless the cases under test need a feature still behind the `experimental` profile, such as the LGMS dataset (id 12). The run records its `ff`, and the run_id ends with it (`20260831T163347Z_prod` versus `20260831T155003Z_prod_experimental`). Never diff or trend two runs with different `ff`: the profiles offer different tools, so the diff would measure the profile, not the release. GOLD cases that need `experimental` are parked (`not doing`) while official runs use the default profile; each one's `status_reason` says when to bring it back. Until late August 2026, dashboards and satellite imagery existed only behind `experimental`, so every GOLD run before 2026-08-31 used `ff=experimental`; do not compare those runs with later default-profile runs.

**Record semantic changes.** If check semantics changed since the previous run, pass `--note "<what changed>"`. It is stored on the run, so later diffs are not read as agent changes.

**Local runs.** `--env local` targets a project-zeno API on `http://localhost:8000` (`make api` in a project-zeno checkout) and reads only `API_TOKEN`. Local runs are smoke runs: a local stack does not match staging or prod, so never commit or diff them.

**Killed runs.** A run appends each finished case to `results/<suite>/runs/<run_id>.partial.jsonl` (gitignored), so a killed run loses only the cases that were in progress. `uv run evals run --suite <suite> --resume <run_id>` finishes it, with the suite the run used, because the partial file is found under that suite's results directory. The settings come from that file (every other flag except `--results-dir` is ignored), it refuses if the case set has changed, and the final record carries `resumed: true`.

**Workers and timeouts.** By default 10 cases run at once (the hard cap is 20), and a trial that takes over 900 seconds becomes an error row. Runs record both settings. A block of timeouts late in a run usually means the API is overloaded: lower `--workers` before blaming the agent.

## CHALLENGE

CHALLENGE asks "how well does the agent answer questions like this?" Its cases sit in a hierarchy, **set, cohort, case**, at `cases/challenge/<set>/<cohort>/<id>.yaml`, and its verdicts are pass rates per set and cohort, never regression counts. Many cases are expected to fail: never triage those failures as regressions, and never change a case to make it pass. Read [cases/challenge/README.md](cases/challenge/README.md) before you touch the set.

```bash
# canonical run (published rates): prod, default profile, 3 trials
uv run evals run --suite challenge --env prod --trials 3 \
  --status-exclude "not doing,todo" --build "<label>"

# roll it up: pass rates per set and cohort against TARGETS.yml
uv run python tools/challenge_rollup.py results/challenge/runs/<run_id>.json
```

### After a CHALLENGE run

Roll the run up, write `results/challenge/recommendations/<run_id>.md`, then commit the run and the recommendations doc together with a regenerated `results/index.json`. The steps are in [cases/challenge/README.md, After every run](cases/challenge/README.md#after-every-run).

## BENCHMARK

BENCHMARK asks "is the agent getting better on a fixed exam?" A version is a manifest, `benchmarks/<version>.json`, that lists CHALLENGE cases by uid; it has no cases of its own. Editing a member case gives it a new uid, which drops it from the version, so a frozen version's members are never edited. Its canonical runs are the North Star trend, and each one's page data is what the frontend AI accuracy scorecards page shows. Read [benchmarks/README.md](benchmarks/README.md) first.

```bash
uv run evals run --benchmark benchmarks/2026-draft-5.json --env prod --trials 3 --build "<label>"
```

### After a BENCHMARK run

Roll the run up with `tools/challenge_rollup.py --benchmark`, write the page data with `tools/benchmark_page.py` on the machine that ran the run, regenerate `results/index.json`, write the recommendations doc, and commit them together. The steps and their order are in [benchmarks/README.md, After a run](benchmarks/README.md#after-a-run). The page data is a contract with the frontend: [Page data contract](benchmarks/README.md#page-data-contract).

## The plain baseline

`tools/plain_baseline.py` asks Sonnet with web search the BENCHMARK `2026-draft-5` questions and scores its replies against the agent's, on the reply only. Its output goes to `results/plain/`, never to `results/benchmark/`, so the frontend cannot show it. Its `ask` step spends API budget: run it only with AJ's go-ahead. The steps, files and keys are in [results/plain/README.md](results/plain/README.md).

## Changing cases

Read [cases/README.md](cases/README.md) before writing or editing a case: it describes the stores, the case file, and how a case's [status](cases/README.md#status-lifecycle) moves. How to write a good case depends on the store: [cases/challenge/README.md](cases/challenge/README.md) for CHALLENGE, [cases/GOLD-AUTHORING.md](cases/GOLD-AUTHORING.md) for the GOLD legacy copy.

After any change to a case file (query, expected values, status, set, group, notes, or a new or deleted case), run these for the store you changed and commit their output in the same commit as the edit:

```bash
# CHALLENGE
uv run python tools/check.py --fix --suite challenge      # recompute uids and MANIFEST.json
uv run python tools/coverage_doc.py --suite challenge     # regenerate COVERAGE.md, coverage.json, cases_index.json
uv run python tools/check_benchmark.py                    # did the edit drop a BENCHMARK member?

# GOLD (legacy copy): edit cases/v2 only; cases/v1 is frozen
uv run python tools/check.py --fix --suite gold
uv run python tools/coverage_doc.py --suite gold
uv run python tools/audit_cases.py --strict               # depth rule and DON'Ts, as CI runs it
```

`check_benchmark.py` matters because editing a `ready` member case gives it a new uid, so the draft BENCHMARK version that listed it no longer runs it. The tool warns on a draft and fails on a frozen version ([benchmarks/README.md](benchmarks/README.md)).

CI runs `check.py` (without `--fix`) on every store (`cases/v1`, `cases/v2`, `cases/challenge`), `coverage_doc.py --check` on `cases/v2` and `cases/challenge`, `audit_cases.py --strict` on `cases/v2` ([The audit gate](cases/GOLD-AUTHORING.md#the-audit-gate)) and `check_benchmark.py`. It fails the PR if a uid or manifest is out of date, a coverage file is stale, the audit finds a violation, or a frozen BENCHMARK version lost a member.

Editing the query or any expected value gives the case a new uid, so earlier results no longer match it. That is intended: it keeps every score pinned to the content it measured. Say in the PR which cases changed and why; the PR is the only record of the reason.

When project-zeno adds, removes or changes a dataset, refresh the catalogue snapshot with `uv run python tools/sync_zeno_catalog.py`, then run `coverage_doc.py` for each store and commit them together.

## How scoring reads

Every check scores `1.0` (pass), `0.0` (fail) or `null` (not evaluated). Each check's documentation says whether a missing input counts as `null` or `0.0`, because a `null` that should have been a fail hides a regression.

Checks roll up into five buckets, one per stage of the agent's work, so a failure points at the stage that broke:

| Bucket | The question it answers |
|---|---|
| Retrieval | Did the agent understand the question and fetch the right data (place, dataset, dates)? |
| Analysis | Are the numbers right? |
| Explanation | Is the prose faithful to the data? |
| Output | Are charts and dashboards presented correctly? |
| Scope | Did it do the right kind of work: answer with data, suggest datasets, ask the user to choose, or decline? |

Most checks belong to one bucket. A few are shared by two, because their failure cannot be pinned on one, and bucket tables report the two kinds separately. The [evaluators README index](src/goldset/evaluators/README.md#index) maps every check to its bucket.

Info-only checks are recorded and reported but never affect a row verdict or GOLD's release gate. They are new or unreliable checks that have not yet earned a vote; [Info-only checks](src/goldset/evaluators/README.md#info-only-checks) lists them with the condition each must meet to gate again.

A run is read through row verdicts and per-bucket tallies, never a flat mean. Each attempt (one trial of one case) passes when every gating check it scored passed, and fails when one scored `0.0`. Each row (one case's result) gets one verdict from its attempts (since 2026-10-28; before, from each check's majority across trials):

- `pass`: most of its scored attempts passed;
- `fail`: they did not (a tie fails);
- `error`: no attempt could be scored (the harness failed after the reply, or the judge failed), so the row measured nothing reliable; rerun it before trusting it. It never counts as a fail;
- `uncovered`: no gating check was evaluated, so it never counts as a pass.

An attempt that got no reply (Horizon's stream stalled, dropped or failed: `no_answer`) is a failed attempt, not an error. An attempt the harness could not score is left out (since 2026-10-27).

**Multi-turn cases** run all their turns in one thread. Per-turn checks are prefixed with the turn number (`t2.aoi_id_match`), and `state_delta` scores the expected changes between turns. A turn that errors ends its conversation, so later turns are not scored against a broken thread.

The tools fail loudly when nothing was measured: `flakiness.py` marks a partial sample INSUFFICIENT DATA instead of calling it stable, `diff_runs.py --fail-on-coverage-loss` fails when checks stop being evaluated, and each report's reconciliation line compares the checks a case should have produced with those actually evaluated.
